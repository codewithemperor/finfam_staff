   141→# Mailjet
   142→
   143→for transactional delivery.

   148→
   149→```text
   150→POST https://api.mailjet.com/v3.1/send

   295→Do NOT send merely because someone loaded a page.

   302→
   303→```text

   321→ORIENTATION_COMPLETED

   325→
   326→* orientation completed
   327→* assessment is next
   328→* Continue Application link
   329→

   331→
   332→---
   333→
   334→## Assessment Passed
   335→

   337→ASSESSMENT_PASSED
   338→```
   339→
   340→Tell the candidate:

   342→* assessment was successful

   345→
   346→Do not expose correct answers.
   347→
   348→---
   349→
   350→## Assessment Failed
   351→

   353→ASSESSMENT_FAILED

   355→
   356→Tell the candidate:

   358→* assessment result
   359→* current application status
   360→* retry information only if current business rules actually permit it

   362→Do not invent retry promises.
   363→
   364→Do not expose answer keys.

   366→---
   367→
   368→## Agreement Accepted
   369→
   370→```text
   371→AGREEMENT_ACCEPTED
   372→```

   378→* Continue Application link

   380→---
   381→
   382→## Appointment Issued
   383→

   385→APPOINTMENT_ISSUED

   388→Include:
   389→
   390→* candidate name

   451→# 9. NOTIFICATION DELIVERY RECORD
   452→
   453→Do not make email sending invisible/untraceable.
   454→
   455→Introduce a small persistence model such as:
   456→
   457→```text
   458→NotificationDelivery
   459→```
   460→
   461→The exact schema should be the smallest robust design.
   462→
   463→It should support:
   464→
   465→* candidate relation where applicable
   466→* notification type
   467→* unique dedupe key
   468→* recipient email snapshot
   469→* template/content version
   470→* provider
   471→* provider message ID if returned
   472→* status
   473→* attempt count
   474→* sent timestamp
   475→* last attempt timestamp
   476→* safe error code/message
   477→* created/updated timestamps
   478→
   479→Do NOT store email API credentials.
   480→
   481→Avoid storing full rendered HTML unless there is a real auditing requirement.
   482→
   483→---
   484→
   485→# 10. DELIVERY STATUS
   486→
   487→Use a small status model.
   488→
   489→Conceptually:
   490→
   491→```text
   492→PENDING
   493→SENT
   494→FAILED
   495→```
   496→
   497→Do not claim:
   498→
   499→```text
   500→DELIVERED
   501→```
   502→
   503→simply because Mailjet accepted the API request.
   504→
   505→`SENT` in this MVP means:
   506→
   507→> Mailjet accepted the transactional send request.
   508→
   509→Actual inbox delivery/bounces require provider events/webhooks and are a separate concern.
   510→
   511→Document that distinction.
   512→
   513→---
   514→
   515→# 11. IDEMPOTENCY
   516→
   517→A lifecycle transition must never generate duplicate email because:
   518→
   519→* user double-clicked
   520→* request retried
   521→* route refreshed
   522→* two concurrent requests occurred
   523→* application server retried work
   524→
   525→Use a stable:
   526→
   527→```text
   528→dedupeKey
   529→```
   530→
   531→with a unique constraint.
   532→
   533→Examples:
   534→
   535→```text
   536→APPLICATION_RECEIVED:<candidateId>
   537→
   538→ORIENTATION_COMPLETED:<candidateId>
   539→
   540→ASSESSMENT_PASSED:<attemptId>
   541→
   542→AGREEMENT_ACCEPTED:<agreementId>
   543→
   544→APPOINTMENT_ISSUED:<appointmentId>
   545→
   546→STAFF_ACTIVATED:<staffId>
   547→
   548→ONBOARDING_STARTED:<onboardingId>
   549→
   550→ONBOARDING_COMPLETED:<onboardingId>
   551→```
   552→
   553→Use immutable database IDs internally.
   554→
   555→Do not rely on email address alone.
   556→
   557→---
   558→
   559→# 12. TRANSACTIONAL OUTBOX PRINCIPLE
   560→
   561→Do NOT make core recruitment progression depend directly on Mailjet being online.
   562→
   563→Example:
   564→
   565→A candidate accepts the agreement.
   566→
   567→This should NOT happen:
   568→
   569→```text
   570→Call Mailjet
   571→↓
   572→Mailjet times out
   573→↓
   574→Rollback agreement acceptance
   575→```
   576→
   577→Instead:
   578→
   579→```text
   580→Business transaction succeeds
   581→+
   582→notification delivery/outbox row is created
   583→↓
   584→transaction commits
   585→↓
   586→attempt Mailjet delivery
   587→```
   588→
   589→A temporary email outage must not corrupt recruitment state.
   590→
   591→---
   592→
   593→# 13. BUSINESS TRANSACTION INTEGRATION
   594→
   595→Where practical, create the notification delivery/outbox record in the SAME database transaction as the meaningful state transition.
   596→
   597→Examples:
   598→
   599→```text
   600→Orientation completed
   601→+
   602→ORIENTATION_COMPLETED notification queued
   603→```
   604→
   605→```text
   606→Appointment issued
   607→+
   608→APPOINTMENT_ISSUED notification queued
   609→```
   610→
   611→```text
   612→Staff activated
   613→+
   614→STAFF_ACTIVATED notification queued
   615→```
   616→
   617→This guarantees that a committed business event always has a corresponding notification intent.
   618→
   619→---
   620→
   621→# 14. DELIVERY FAILURE
   622→
   623→If Mailjet fails after the business transaction has committed:
   624→
   625→* recruitment/staff action remains successful
   626→* mark notification appropriately
   627→* log safe server-side diagnostic information
   628→* never expose Mailjet secrets
   629→* do not return a false recruitment failure to the candidate
   630→
   631→The user should not have to repeat Agreement acceptance or Staff Activation just because email failed.
   632→
   633→---
   634→
   635→# 15. RETRY DESIGN
   636→
   637→Implement a reusable retry-capable service.
   638→
   639→At minimum support:
   640→
   641→```text
   642→sendNotification(deliveryId)
   643→retryNotification(deliveryId)
   644→retryPendingNotifications(...)
   645→```
   646→
   647→Do not blindly retry forever.
   648→
   649→Use a reasonable bounded attempt policy/config.
   650→
   651→If there is no deployment scheduler yet:
   652→
   653→* implement the retry service
   654→* document that recurring automatic retry scheduling requires deployment infrastructure
   655→
   656→Do not secretly invent a cron environment.
   657→
   658→A protected future scheduler/worker can call the service.
   659→
   660→---
   661→
   662→# 16. DO NOT SEND EMAIL INSIDE DATABASE TRANSACTIONS
   663→
   664→Mailjet network calls must NOT happen while a Prisma transaction is holding database locks.
   665→
   666→Correct sequence:
   667→
   668→```text
   669→transaction:
   670→  update domain state
   671→  create NotificationDelivery
   672→
   673→commit
   674→
   675→then:
   676→  attempt Mailjet send
   677→```
