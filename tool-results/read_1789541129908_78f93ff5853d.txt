   318→   318→/// The candidate's issued Provisional Letter of Appointment — stage 4 of
   319→   319→/// the journey. Issued lazily and exactly once, server-side, when an
   320→   320→/// OFFER_ACCEPTED candidate first opens the appointment stage
   321→   321→/// (src/server/services/appointment.ts); viewing again is a read-only
   322→   322→/// record and NEVER re-issues or mutates the letter.
   323→   323→///
   324→   324→/// Hybrid historical-integrity model: the columns below are the immutable,
   325→   325→/// candidate-specific SNAPSHOT (who, which letter, when, under which
   326→   326→/// content version) while the letter TEXT itself lives in an append-only
   327→   327→/// content registry (src/config/appointment.ts, APPOINTMENT_CONTENT_
   328→   328→/// VERSIONS) resolved by `version`. An appointment issued under v1.0 must
   329→   329→/// stay reproducible as v1.0 forever — later wording changes append new
   330→   330→/// registry versions and never touch issued ones. There is deliberately no
   331→   331→/// separate effectiveDate column: the letter date IS `issuedAt` for the
   332→   332→/// MVP (docs/CONTENT-QUESTIONS.md §23 keeps the distinction open).

   343→   343→  /// under. Immutable after issuance.

   438→   438→/// The Staff member's authenticated Staff Portal access (Stage 7). One row
   439→   439→/// per Staff record, created in the SAME transaction as the Staff row by
   440→   440→/// staff activation (and idempotently by the backfill script for pre-existing
   441→   441→/// Staff). The account owns login codes and portal sessions and carries the
   442→   442→/// future suspension flag — nothing else:
   443→   443→///
   444→   444→/// - It duplicates NO identity data. Name, email, phone and appointment
   445→   445→///   facts are reached through StaffAccount → Staff → Candidate; the login
   446→   446→///   email IS the candidate's registered email (brief §3/§4).
   447→   447→/// - It stores NO credentials. Login is email OTP (hashed codes live on
   448→   448→///   StaffLoginCode); sessions are DB rows with only the token hash
   449→   449→///   (StaffSession).
   450→   450→/// - status = SUSPENDED blocks code requests, verification and session
   451→   451→///   resolution; there is deliberately no admin UI in this stage.
   452→   452→model StaffAccount {
   453→   453→  id      String             @id @default(cuid())
   454→   454→  /// One portal account per Staff identity.
   455→   455→  staffId String             @unique

   586→   586→/// Transactional email delivery record (outbox pattern, brief §9).
   587→   587→///
   588→   588→/// One row per lifecycle notification INTENT. Rows are created by the
   589→   589→/// central notification service in the SAME database transaction as the
   590→   590→/// meaningful state change they belong to (brief §13), so a committed
   591→   591→/// business event always has a corresponding notification intent even if
   592→   592→/// the email provider is down. The unique `dedupeKey` is the exactly-once
   593→   593→/// latch: user double-clicks, request retries, concurrent requests and
   594→   594→/// route refreshes can never queue a duplicate email (brief §11).
   595→   595→///
   596→   596→/// The actual Mailjet network call happens AFTER the business transaction
   597→   597→/// commits — never while the transaction holds database locks (§16). A
   598→   598→/// Mailjet outage therefore marks rows FAILED/PENDING but can never roll
   599→   599→/// back or corrupt recruitment state (§12/§14).
   600→   600→///
   601→   601→/// No credentials are ever stored here; no rendered HTML is stored — the
   602→   602→/// email body is re-derived from immutable snapshot data at send time so
   603→   603→/// retries stay faithful (staff/appointment/agreement/attempt snapshot
   604→   604→/// rows are immutable by schema design).
   605→   605→model NotificationDelivery {
   606→   606→  id        String             @id @default(cuid())
   607→   607→  /// The candidate the notification belongs to, where applicable. Cascade
   608→   608→  /// delete mirrors every other candidate-owned record.
   609→   609→  candidateId String?
   610→   610→  candidate Candidate?         @relation(fields: [candidateId], references: [id], onDelete: Cascade)
   611→   611→  /// Stable lifecycle key (NotificationType).
   612→   612→  type      NotificationType
   613→   613→  /// Stable idempotency key "<TYPE>:<immutable entity id>" (e.g.
   614→   614→  /// "APPLICATION_RECEIVED:<candidateId>", "ASSESSMENT_PASSED:<attemptId>",
   615→   615→  /// "STAFF_ACTIVATED:<staff row id>"). Unique — the exactly-once latch.
   616→   616→  dedupeKey String             @unique
   617→   617→  /// Recipient email snapshotted at enqueue time (never re-read at send).

   626→   626→  /// PENDING until the provider accepts a send; SENT once accepted
