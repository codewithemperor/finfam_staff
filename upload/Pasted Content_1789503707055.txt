# PART A

# MAILJET TRANSACTIONAL NOTIFICATION SERVICE

The recruitment journey already includes:

```text
Application
→ Orientation
→ Assessment
→ Agreement
→ Provisional Appointment
→ Staff Activation
→ Onboarding
```

Email is NOT another recruitment stage.

It is a:

# CROSS-CUTTING PLATFORM SERVICE

The notification system should keep applicants/staff informed whenever an important lifecycle event occurs.

Do NOT add email logic directly inside UI components.

Do NOT scatter raw Mailjet API calls across recruitment services.

Build one reusable notification architecture.

# 3. MAILJET PROVIDER

Use:

# Mailjet

for transactional delivery.

Use the current Mailjet transactional Send API.

Prefer:

```text
POST https://api.mailjet.com/v3.1/send
```

with server-side authentication.

Native server-side `fetch` is acceptable and is preferred if it avoids adding an unnecessary dependency.

If the official Mailjet Node SDK already fits the existing application cleanly, it may be used, but do not add a dependency simply for convenience.

No Mailjet code must reach the browser bundle.

# 9. NOTIFICATION DELIVERY RECORD

Do not make email sending invisible/untraceable.

Introduce a small persistence model such as:

```text
NotificationDelivery
```

The exact schema should be the smallest robust design.

It should support:

* candidate relation where applicable
* notification type
* unique dedupe key
* recipient email snapshot
* template/content version
* provider
* provider message ID if returned
* status
* attempt count
* sent timestamp
* last attempt timestamp
* safe error code/message
* created/updated timestamps

Do NOT store email API credentials.

Avoid storing full rendered HTML unless there is a real auditing requirement.

# 10. DELIVERY STATUS

Use a small status model.

Conceptually:

```text
PENDING
SENT
FAILED
```

Do not claim:

```text
DELIVERED
```

simply because Mailjet accepted the API request.

`SENT` in this MVP means:

> Mailjet accepted the transactional send request.

Actual inbox delivery/bounces require provider events/webhooks and are a separate concern.

Document that distinction.

---

# 11. IDEMPOTENCY

A lifecycle transition must never generate duplicate email because:

* user double-clicked
* request retried
* route refreshed
* two concurrent requests occurred
* application server retried work

Use a stable:

```text
dedupeKey
```

with a unique constraint.

Examples:

```text
APPLICATION_RECEIVED:<candidateId>

ORIENTATION_COMPLETED:<candidateId>

ASSESSMENT_PASSED:<attemptId>

AGREEMENT_ACCEPTED:<agreementId>

APPOINTMENT_ISSUED:<appointmentId>

STAFF_ACTIVATED:<staffId>

ONBOARDING_STARTED:<onboardingId>

ONBOARDING_COMPLETED:<onboardingId>
```

Use immutable database IDs internally.

Do not rely on email address alone.

---

# 12. TRANSACTIONAL OUTBOX PRINCIPLE

Do NOT make core recruitment progression depend directly on Mailjet being online.

Example:

A candidate accepts the agreement.

This should NOT happen:

```text
Call Mailjet
↓
Mailjet times out
↓
Rollback agreement acceptance
```

Instead:

```text
Business transaction succeeds
+
notification delivery/outbox row is created
↓
transaction commits
↓
attempt Mailjet delivery
```

A temporary email outage must not corrupt recruitment state.

---

# 13. BUSINESS TRANSACTION INTEGRATION

Where practical, create the notification delivery/outbox record in the SAME database transaction as the meaningful state transition.

Examples:

```text
Orientation completed
+
ORIENTATION_COMPLETED notification queued
```

```text
Appointment issued
+
APPOINTMENT_ISSUED notification queued
```

```text
Staff activated
+
STAFF_ACTIVATED notification queued
```

This guarantees that a committed business event always has a corresponding notification intent.

---

# 14. DELIVERY FAILURE

If Mailjet fails after the business transaction has committed:

* recruitment/staff action remains successful
* mark notification appropriately
* log safe server-side diagnostic information
* never expose Mailjet secrets
* do not return a false recruitment failure to the candidate

The user should not have to repeat Agreement acceptance or Staff Activation just because email failed.

---

# 15. RETRY DESIGN

Implement a reusable retry-capable service.

At minimum support:

```text
sendNotification(deliveryId)
retryNotification(deliveryId)
retryPendingNotifications(...)
```

Do not blindly retry forever.

Use a reasonable bounded attempt policy/config.

If there is no deployment scheduler yet:

* implement the retry service
* document that recurring automatic retry scheduling requires deployment infrastructure

Do not secretly invent a cron environment.

A protected future scheduler/worker can call the service.

---

# 16. DO NOT SEND EMAIL INSIDE DATABASE TRANSACTIONS

Mailjet network calls must NOT happen while a Prisma transaction is holding database locks.

Correct sequence:

```text
transaction:
  update domain state
  create NotificationDelivery

commit

then:
  attempt Mailjet send
```
